* ห้ามทำ Login เดิมพัง

1. เป้าหมายของงาน
   ==================================================

เพิ่มระบบ “มอบหมายงานผ่านตารางงาน / Work Order Assignment” จากระบบเดิมที่เคยใช้ใน Google Sheet ให้มาอยู่ใน WebApp

หลักการทำงาน:

A หรือ Admin / ผู้มีสิทธิ์มอบหมายงาน สร้างและมอบหมายงานให้ B หรือ Staff / Technician

ข้อมูลที่ใช้ในงานจริงมีดังนี้:

* เวลา ไม่บังคับ
* เลขห้อง
* ตึก
* ชั้น
* ชื่อผู้ติดต่อ
* เบอร์ผู้ติดต่อ
* เหตุที่เกิด
* รูปภาพประกอบ
* ผู้มอบหมาย
* ผู้ได้รับมอบหมาย
* สถานะงาน
* หมายเหตุ

เมื่อมีการมอบหมายงาน ระบบต้องตรวจสอบว่าในช่วงเวลานั้นผู้ได้รับมอบหมายมีงานอื่นอยู่แล้วหรือไม่

เมื่อผู้ได้รับมอบหมายได้รับงาน งานนั้นต้องไปแสดงในหน้า “งานของฉัน” ของผู้ได้รับมอบหมายคนนั้นเท่านั้น ยกเว้นผู้มีสิทธิ์ดูภาพรวม เช่น Admin

3. สถานะงานใหม่
===============

ให้ใช้สถานะหลักดังนี้:

1. received
   label: รับเรื่อง

2. pending_inspection
   label: รอตรวจสอบ

3. inspected_waiting_repair
   label: ตรวจสอบแล้วรอแก้ไข/อะไหล่

4. completed
   label: แก้ไขสมบูรณ์แล้วเรียบร้อยแล้ว

5. repaired_follow_up
   label: แก้ไขแล้ว รอติดตาม

6. temporary_waiting_parts
   label: แก้ไขเบื้องต้น รออะไหล่/ผู้รับเหมา

7. rejected
   label: ปฏิเสธงาน

เพิ่มสถานะ/ตัวกรองเสริมสำหรับงานที่ช่างแจ้งว่าเสร็จแล้วแต่ยังไม่มี PIN:

subStatus: waiting_owner_or_admin_verification
label: ช่างแจ้งเสร็จแล้ว รอตรวจสอบ

กฎสำคัญ:

* งานที่มี subStatus = waiting_owner_or_admin_verification ห้ามนับเป็น completed
* ห้ามนับเป็นงานเสร็จสิ้นใน Dashboard
* ห้ามนับเป็นงานเสร็จสิ้นใน Report รายเดือน/รายปี
* ต้องนับเป็น “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ”
* จะเป็น completed ได้ต่อเมื่อ Admin / ผู้มอบหมาย / เจ้าของห้อง กดยืนยันปิดงานเท่านั้น

ให้ยังรองรับ status เดิมโดย map ดังนี้:

* open = เปิดงาน / ยังไม่มอบหมาย
* waiting = เปิดงาน / ยังไม่มอบหมาย
* in_progress = received
* inspecting = pending_inspection
* waiting_repair = inspected_waiting_repair
* done = completed
* completed = completed
* follow_up = repaired_follow_up
* temporary_waiting = temporary_waiting_parts

=============================

ปรับฟอร์มสร้างงานใหม่ให้มี field ดังนี้:

* วันที่งาน บังคับ
* เวลาเริ่มงาน ไม่บังคับ
* เวลาสิ้นสุด ไม่บังคับ
* เลขห้อง บังคับ
* ตึก ไม่บังคับ
* ชั้น ไม่บังคับ
* ชื่อผู้ติดต่อ บังคับ
* เบอร์ผู้ติดต่อ บังคับ
* เหตุที่เกิด / รายละเอียดงาน บังคับ
* รูปภาพประกอบ ขั้นต่ำ 0 รูป สูงสุด 3 รูป
* ผู้มอบหมาย ใช้ currentUser
* ผู้ได้รับมอบหมาย เลือกจาก Staff / Technician เท่านั้น
* หมายเหตุ ไม่บังคับ

เมื่อสร้างงาน:

* Generate job id ตามระบบเดิม
* Generate PIN 4 หลัก เช่น 0000-9999
* ถ้าเป็นไปได้ ห้ามซ้ำกับงาน active
* บันทึก closePin ลงใน job
* บันทึก timeline ว่าสร้างงานเมื่อไร โดยใคร
* ถ้ามี assignee ให้บันทึก timeline ว่ามอบหมายให้ใคร
* ถ้าไม่มี assignee ให้งานเข้า Pool งานกลาง

การแสดง PIN:

* Admin เห็น PIN
* ผู้มอบหมายเห็น PIN
* เจ้าของห้อง / ผู้แจ้งเห็น PIN
* ผู้ได้รับมอบหมายไม่เห็น PIN
* ผู้ได้รับมอบหมายจะเห็นเฉพาะช่องให้กรอก PIN ตอนต้องการปิดงาน

5. ตรวจสอบเวลางานทับซ้อน
========================

เมื่อ Admin หรือผู้มีสิทธิ์มอบหมายงานเลือกผู้ได้รับมอบหมาย และกรอกช่วงเวลา startTime / endTime ให้ระบบตรวจสอบงานของ assignee คนนั้นว่ามีงานอื่นในช่วงเวลานั้นหรือไม่

เงื่อนไข:

* ตรวจเฉพาะงานที่ยังไม่ completed และไม่ rejected
* ถ้างานใหม่ไม่มีเวลา ไม่ต้องตรวจ overlap
* ถ้ามี startTime แต่ไม่มี endTime ให้ถือว่าเป็น slot 1 ชั่วโมง
* ถ้ามี endTime แต่ไม่มี startTime ให้แจ้ง validation ว่าต้องมีเวลาเริ่ม
* ถ้ามีงานทับซ้อน ให้แสดง confirm modal ก่อนสร้างงาน

ข้อความใน modal:

“ผู้ได้รับมอบหมายคนนี้มีงานอยู่ในช่วงเวลาดังกล่าว:

[เวลา] [เลขงาน] [รายละเอียดสั้น ๆ]

ยืนยันที่จะมอบหมายงานซ้อนหรือไม่?

หากยืนยัน กรุณาโทรแจ้งผู้ได้รับมอบหมายที่เบอร์ [เบอร์เจ้าหน้าที่] ก่อนดำเนินการ”

ปุ่ม:

* ยกเลิก
* ยืนยันมอบหมายงานซ้อน

ถ้ากดยกเลิก:

* ห้ามสร้างงาน
* ห้ามมอบหมายงาน

ถ้ากดยืนยัน:

* สร้างงาน / มอบหมายงานตามปกติ
* set hasScheduleConflict = true
* บันทึก conflictConfirmedAt
* บันทึก conflictConfirmedBy
* เพิ่ม timeline log:
  “มอบหมายงานซ้อนช่วงเวลา โดยได้รับการยืนยันจาก [ชื่อผู้ใช้]”

8. กฎการเปลี่ยนสถานะ
====================

ใน Job Detail Modal ให้มีปุ่ม “อัปเดตสถานะ”

เมื่อกดแล้วให้แสดงฟอร์มเลือกสถานะ และแสดง field แบบ dynamic ตามสถานะที่เลือก

---

## สถานะ 1: รับเรื่อง

เมื่อเลือก “รับเรื่อง”

Field เพิ่มเติม:

* ไม่ต้องกรอกข้อมูลเพิ่ม

เมื่อกดยืนยัน:

* เปลี่ยน status เป็น received
* บันทึก acceptedAt เป็นวันเวลาปัจจุบัน
* เพิ่ม timeline log:
  “รับเรื่องไว้เมื่อ [วันเวลา] โดย [ชื่อผู้ใช้]”

---

## สถานะ 2: รอตรวจสอบ

เมื่อเลือก “รอตรวจสอบ”

Field เพิ่มเติม:

* วันที่เข้าตรวจสอบ inspectionDate บังคับ

Validation:

* ต้องเลือกวันที่เข้าตรวจสอบ

เมื่อกดยืนยัน:

* เปลี่ยน status เป็น pending_inspection
* บันทึก inspectionDate
* เพิ่ม timeline log:
  “รอตรวจสอบ โดยกำหนดวันที่เข้าตรวจสอบเป็น [วันที่] บันทึกโดย [ชื่อผู้ใช้]”

---

## สถานะ 3: ตรวจสอบแล้วรอแก้ไข/อะไหล่

ใช้เงื่อนไขนี้เท่านั้น และลบเงื่อนไขสถานะ 3 ที่ซ้ำออกทั้งหมด

เมื่อผู้ได้รับมอบหมายเลือกสถานะนี้ ต้องแสดง field ดังนี้:

* วันที่ตรวจสอบ / วันที่อัปเดต บังคับ
* แนบรูปภาพ ขั้นต่ำ 1 รูป สูงสุด 3 รูป บังคับ
* กล่องข้อความที่ 1: สาเหตุ บังคับ
* กล่องข้อความที่ 2: แนวทางแก้ไข บังคับ
* กล่องข้อความที่ 3: หมายเหตุ ไม่บังคับ

Validation:

* ต้องเลือกวันที่ก่อนบันทึก
* ต้องแนบรูปภาพอย่างน้อย 1 รูป
* ห้ามแนบเกิน 3 รูป
* ต้องกรอก “สาเหตุ”
* ต้องกรอก “แนวทางแก้ไข”
* “หมายเหตุ” ไม่บังคับ

เมื่อกดยืนยัน:

* เปลี่ยน status เป็น inspected_waiting_repair
* บันทึกวันที่ตรวจสอบ / วันที่อัปเดต
* บันทึกรูปภาพเข้า attachments / statusUpdates
* บันทึก cause จากกล่อง “สาเหตุ”
* บันทึก solution จากกล่อง “แนวทางแก้ไข”
* บันทึก note จากกล่อง “หมายเหตุ” ถ้ามี
* เพิ่ม timeline log:
  “ตรวจสอบแล้วรอแก้ไข/อะไหล่ เมื่อ [วันเวลา] โดย [ชื่อผู้ใช้] สาเหตุ: [สาเหตุ] แนวทางแก้ไข: [แนวทางแก้ไข]”

---

## สถานะ 4: แก้ไขสมบูรณ์แล้วเรียบร้อยแล้ว

สถานะนี้มี 2 กรณี:

A. ลูกบ้านอยู่ และสามารถขอ PIN ได้
B. ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้

เมื่อผู้ได้รับมอบหมายเลือกสถานะนี้ ให้แสดง field ดังนี้:

* วันที่แก้ไขเสร็จ completedWorkDate บังคับ
* แนบรูปภาพ ขั้นต่ำ 1 รูป สูงสุด 3 รูป บังคับ
* หมายเหตุ ไม่บังคับ
* ช่องกรอก PIN 4 หลัก
* Checkbox หรือ Switch:
  “ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้”

ชื่อ field:

* noPinAvailable: boolean
* noPinReason: string
* pendingVerificationAt: datetime

---

## กรณี A: ลูกบ้านอยู่ และสามารถขอ PIN ได้

ถ้า noPinAvailable = false

ระบบต้องบังคับกรอก PIN 4 หลัก

Validation:

* ต้องเลือกวันที่แก้ไขเสร็จ
* ต้องแนบรูปภาพอย่างน้อย 1 รูป
* ห้ามแนบเกิน 3 รูป
* ต้องกรอก PIN
* PIN ที่กรอกต้องตรงกับ job.closePin

ถ้า PIN ไม่ตรง:

* ห้ามปิดงาน
* แสดง error:
  “PIN ไม่ถูกต้อง กรุณาตรวจสอบกับผู้มอบหมายงานหรือเจ้าของห้อง”

ถ้า PIN ถูกต้อง:

* เปลี่ยน status เป็น completed
* ล้าง subStatus ถ้ามี
* บันทึก completedAt เป็นวันเวลาปัจจุบัน
* บันทึก completedWorkDate
* บันทึกรูปภาพ
* บันทึกหมายเหตุ ถ้ามี
* เพิ่ม timeline log:
  “ปิดงานสำเร็จเมื่อ [วันเวลา] โดย [ชื่อผู้ใช้] ด้วย PIN ที่ถูกต้อง”

---

## กรณี B: ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้

ถ้า noPinAvailable = true

ระบบต้องไม่บังคับกรอก PIN

แต่ต้องแสดง field เพิ่มเติม:

* เหตุผลที่ไม่สามารถขอ PIN ได้ noPinReason บังคับ

Placeholder:

“เช่น ลูกบ้านไม่อยู่ห้อง, ลูกบ้านอนุญาตให้เข้าทำงานล่วงหน้า, ติดต่อไม่ได้, ผู้มอบหมายแจ้งให้ดำเนินการก่อน”

Validation:

* ต้องเลือกวันที่แก้ไขเสร็จ
* ต้องแนบรูปภาพอย่างน้อย 1 รูป
* ห้ามแนบเกิน 3 รูป
* ต้องกรอกเหตุผลที่ไม่สามารถขอ PIN ได้
* ไม่ต้องกรอก PIN

เมื่อกดยืนยัน:

* ห้ามเปลี่ยน status เป็น completed
* ห้าม set completedAt
* ห้ามนับเป็นงานเสร็จสิ้น
* ให้เปลี่ยน status เป็น pending_inspection
* ให้ตั้ง subStatus = waiting_owner_or_admin_verification
* label ที่แสดงใน UI:
  “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ”
* บันทึก pendingVerificationAt เป็นวันเวลาปัจจุบัน
* บันทึก completedWorkDate
* บันทึกรูปภาพ
* บันทึกหมายเหตุ ถ้ามี
* บันทึก noPinAvailable = true
* บันทึก noPinReason
* เพิ่ม timeline log:
  “ช่างแจ้งว่าแก้ไขงานเสร็จแล้ว แต่ไม่สามารถขอ PIN ได้ เนื่องจาก [เหตุผล] งานถูกเปลี่ยนเป็นช่างแจ้งเสร็จแล้ว รอตรวจสอบ เมื่อ [วันเวลา] โดย [ชื่อผู้ใช้]”

UX Message หลังบันทึก:

“บันทึกการแก้ไขเรียบร้อยแล้ว แต่งานยังไม่ถูกปิด เนื่องจากไม่มี PIN ระบบเปลี่ยนสถานะเป็นช่างแจ้งเสร็จแล้ว รอตรวจสอบ เพื่อให้ผู้มอบหมายหรือเจ้าของห้องตรวจสอบต่อไป”

ข้อกำหนดสำคัญของกรณีไม่มี PIN:

* งานนี้ห้ามนับเป็น completed
* ห้ามนับเป็นงานเสร็จสิ้นใน Dashboard
* ห้ามนับเป็นงานเสร็จสิ้นใน Report รายเดือน
* ห้ามนับเป็นงานเสร็จสิ้นใน Report รายปี
* ให้นับเป็น “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ”
* completedAt ต้องยังเป็นค่าว่าง
* จะถือว่า completed ได้เฉพาะเมื่อ Admin / ผู้มอบหมาย / เจ้าของห้อง ยืนยันปิดงานภายหลัง

11. Timeline / Log
==================

เพิ่ม timeline ในแต่ละ job เป็น array เช่น:

timeline: [
{
id,
at,
by,
byName,
action,
fromStatus,
toStatus,
message,
data
}
]

ทุก event สำคัญต้องบันทึก timeline:

* สร้างงาน
* มอบหมายงาน
* มอบหมายงานซ้อนเวลา
* รับเรื่อง
* เปลี่ยนสถานะ
* แนบรูป
* ตรวจสอบแล้วรอแก้ไข/อะไหล่
* ช่างแจ้งเสร็จแล้วแต่ไม่มี PIN
* ระบบเปลี่ยนงานเป็นช่างแจ้งเสร็จแล้ว รอตรวจสอบ
* Admin / ผู้มอบหมาย / เจ้าของห้อง ยืนยันปิดงานแทน PIN
* งานถูกส่งกลับให้แก้ไข
* ขอข้อมูลเพิ่มเติม
* ปิดงาน
* ปฏิเสธงาน

ตัวอย่าง log กรณีไม่มี PIN:

{
id: "log_xxx",
at: "2026-06-26T10:30:00+07:00",
by: currentUser.id,
byName: currentUser.name,
action: "complete_without_pin",
fromStatus: "received",
toStatus: "pending_inspection",
message: "ช่างแจ้งว่าแก้ไขงานเสร็จแล้ว แต่ไม่สามารถขอ PIN ได้ เนื่องจากลูกบ้านไม่อยู่ห้อง",
data: {
noPinAvailable: true,
noPinReason: "ลูกบ้านไม่อยู่ห้อง",
subStatus: "waiting_owner_or_admin_verification",
attachmentsCount: 3
}
}

12. สิทธิ์การใช้งาน
===================

Admin:

* สร้างงานได้
* มอบหมายงานได้
* เห็นทุกงาน
* เห็น PIN
* ดู timeline ทุกงาน
* แก้ไขผู้รับผิดชอบได้
* ยืนยันปิดงานกรณีไม่มี PIN ได้
* ส่งกลับให้แก้ไขได้
* ขอข้อมูลเพิ่มเติมได้

Staff / Technician:

* เห็นเฉพาะงานตัวเอง
* เปลี่ยนสถานะงานตัวเองได้
* ไม่เห็น PIN
* ต้องกรอก PIN ตอนปิดงาน ถ้าลูกบ้านอยู่
* เลือก “ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้” ได้
* ถ้าเลือกไม่มี PIN งานต้องเปลี่ยนเป็น “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ” ไม่ใช่ completed

Resident:

* เห็นเฉพาะงานของห้องตัวเอง
* เห็นสถานะและ timeline แบบสรุป
* เห็น PIN เฉพาะกรณีเป็นเจ้าของห้อง / ผู้แจ้งของงานนั้น
* ห้ามเปลี่ยนสถานะงาน
* สามารถยืนยันปิดงานได้ เฉพาะงานของห้องตัวเองที่ subStatus = waiting_owner_or_admin_verification

Co-Admin / ผู้มีสิทธิ์มอบหมายงาน:

* ใช้ permission เดิมของระบบ
* ถ้ามี canAssign ให้มอบหมายงานได้
* เห็นงานตามสิทธิ์เดิม
* ถ้ามี canVerifyCompletion ให้ยืนยันปิดงานกรณีไม่มี PIN ได้

17. Acceptance Criteria
=======================

ถือว่างานเสร็จเมื่อ:

1. Admin สร้างงานพร้อมข้อมูลครบตามฟอร์มใหม่ได้
2. Admin มอบหมายงานให้ Staff ได้
3. ถ้าเวลาของ Staff ทับซ้อน ระบบแจ้งเตือนก่อนมอบหมาย
4. ถ้ายืนยันมอบหมายงานซ้อน ระบบบันทึกงานและ log ได้
5. Staff เห็นงานนั้นใน “งานของฉัน” เท่านั้น
6. Staff เปลี่ยนสถานะตาม 7 สถานะได้
7. แต่ละสถานะแสดง field บังคับแตกต่างกันตามกฎ
8. ถ้ากรอกข้อมูลไม่ครบ ระบบไม่ให้บันทึก
9. สถานะ 3 ต้องใช้เงื่อนไขอันแรกเท่านั้น คือ วันที่ + รูป 1-3 รูป + สาเหตุ + แนวทางแก้ไข + หมายเหตุ
10. สถานะ 3 ต้องบังคับกรอกสาเหตุและแนวทางแก้ไข
11. สถานะ completed ต้องกรอก PIN 4 หลักให้ถูกต้องก่อนปิดงาน ถ้าไม่ได้เลือกกรณีไม่มี PIN
12. ถ้า Staff เลือก “ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้” ระบบต้องไม่บังคับกรอก PIN
13. ถ้าเลือกไม่มี PIN ระบบต้องบังคับกรอกเหตุผล
14. ถ้าเลือกไม่มี PIN ระบบต้องบังคับแนบรูปอย่างน้อย 1 รูป
15. ถ้าเลือกไม่มี PIN งานต้องไม่กลายเป็น completed
16. ถ้าเลือกไม่มี PIN งานต้องเปลี่ยนเป็น “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ”
17. งานที่ไม่มี PIN ต้องไม่ถูกนับเป็นงานเสร็จสิ้น
18. งานที่ไม่มี PIN ต้องไม่ถูกนับใน Report ว่า Completed
19. Admin / ผู้มอบหมาย / เจ้าของห้อง สามารถยืนยันปิดงานภายหลังได้
20. หลัง Admin / ผู้มอบหมาย / เจ้าของห้องยืนยันปิดงานแล้วเท่านั้น งานจึงเปลี่ยนเป็น completed
21. completedAt ต้องถูกบันทึกเฉพาะตอนปิดงานจริง
22. Timeline ของงานบันทึกทุกกิจกรรมสำคัญ
23. Admin เห็น PIN แต่ Staff ไม่เห็น PIN
24. Resident เห็นเฉพาะงานของห้องตัวเอง
25. รูปภาพแนบได้พร้อม preview
26. ข้อมูลยังอยู่หลัง refresh เพราะบันทึกใน localStorage
27. UI ใช้งานได้ดีทั้ง Desktop และ Mobile
28. ไม่มี error ใน console จาก flow หลัก

18. วิธีทดสอบ Flow หลัก
=======================

กรุณาทดสอบอย่างน้อยตามนี้:

Flow A: ปิดงานด้วย PIN

1. Login เป็น Admin
2. สร้างงานใหม่
3. เลือกผู้ได้รับมอบหมาย
4. ตรวจสอบว่า PIN ถูก generate
5. Login เป็น Staff ที่ได้รับมอบหมาย
6. เปิดงานใน “งานของฉัน”
7. เปลี่ยนสถานะเป็น รับเรื่อง
8. เปลี่ยนสถานะเป็น รอตรวจสอบ
9. เปลี่ยนสถานะเป็น ตรวจสอบแล้วรอแก้ไข/อะไหล่
10. กรอกวันที่ แนบรูป กรอกสาเหตุ กรอกแนวทางแก้ไข
11. เปลี่ยนสถานะเป็น แก้ไขสมบูรณ์แล้วเรียบร้อยแล้ว
12. กรอก PIN ถูกต้อง
13. ตรวจสอบว่างานเป็น completed
14. ตรวจสอบว่า completedAt มีค่า
15. ตรวจสอบว่างานนับเป็นเสร็จสิ้นใน Dashboard

Flow B: ไม่มี PIN เพราะลูกบ้านไม่อยู่

1. Login เป็น Admin
2. สร้างงานใหม่และมอบหมายให้ Staff
3. Login เป็น Staff
4. เปิดงานใน “งานของฉัน”
5. เลือกสถานะ แก้ไขสมบูรณ์แล้วเรียบร้อยแล้ว
6. แนบรูปอย่างน้อย 1 รูป
7. ติ๊ก “ลูกบ้านไม่อยู่ / ไม่สามารถขอ PIN ได้”
8. กรอกเหตุผล
9. กดยืนยัน
10. ตรวจสอบว่างานไม่เป็น completed
11. ตรวจสอบว่าสถานะเป็น pending_inspection
12. ตรวจสอบว่า subStatus เป็น waiting_owner_or_admin_verification
13. ตรวจสอบว่า label แสดง “ช่างแจ้งเสร็จแล้ว รอตรวจสอบ”
14. ตรวจสอบว่า completedAt ยังว่าง
15. ตรวจสอบว่า Dashboard ไม่นับเป็นงานเสร็จสิ้น
16. Login เป็น Admin / ผู้มอบหมาย / เจ้าของห้อง
17. เปิดงานนั้น
18. กด “ยืนยันปิดงาน”
19. ตรวจสอบว่างานเปลี่ยนเป็น completed
20. ตรวจสอบว่า completedAt มีค่า
21. ตรวจสอบว่างานจึงถูกนับเป็นเสร็จสิ้นหลังการยืนยัน

Flow C: เวลางานทับซ้อน

1. Login เป็น Admin
2. สร้างงานแรกให้ Staff A เวลา 10:00-11:00
3. สร้างงานที่สองให้ Staff A เวลา 10:30-11:30
4. ตรวจสอบว่าระบบแจ้งเตือนเวลาทับซ้อน
5. กดยกเลิก แล้วตรวจสอบว่างานไม่ถูกสร้าง
6. ลองใหม่ แล้วกดยืนยันมอบหมายงานซ้อน
7. ตรวจสอบว่างานถูกสร้าง
8. ตรวจสอบว่า hasScheduleConflict = true
9. ตรวจสอบว่า timeline มี log การยืนยันมอบหมายงานซ้อน

==================================================
19. หลังแก้เสร็จ
================

กรุณาสรุปให้ด้วยว่า:

* แก้ไฟล์ไหนบ้าง
* เพิ่ม function อะไรบ้าง
* โครงสร้าง job ใหม่เป็นอย่างไร
* วิธีทดสอบ flow Admin → มอบหมาย → Staff รับงาน → เปลี่ยนสถานะ → ปิดงานด้วย PIN
* วิธีทดสอบ flow ไม่มี PIN → ช่างแจ้งเสร็จแล้ว รอตรวจสอบ → Admin/ผู้มอบหมาย/เจ้าของห้องยืนยันปิดงาน
* จุดที่ควรย้ายไป Backend ในอนาคต
* จุดที่ยังเป็น mock/localStorage และยังไม่ควรใช้กับข้อมูลจริง
